## 桌面内核所有权与失败清理

2026-10-30：Windows/Linux 共用 `CoreStore` 生命周期及 `service` facade，分别由
SCM/systemd 持有数据面。`service::required()` 统一平台能力选择；缺失、不可达或版本不符
的服务不会触发 GUI/CLI 自行 spawn，root GUI 也不例外。Linux 普通启动与重启沿已有
显式安装授权流程，应用启动本身仍不自动提权安装。macOS 保留原进程后端。
`CoreProcess::start` / `spawnDetached` 在 Windows/Linux 拒绝应用进程内启动，配置检查与
SRS 工具仍可运行各自有界短任务，不把工具进程当作常驻数据面。

命令入口复用同一 Runtime/缓存或向现存实例转发，不能创建 CLI 专属数据面。CLI 的
一次性 `core start` 可让服务内核在命令 Runtime 退出后驻留；查询不取得停止所有权。
析构只停止当前对象负责且未声明驻留的服务内核或本地子进程；GUI 显式退出继续走共享
异步收尾，显式 STOP 仍可处理上次异常退出后遗留的所属服务内核。

两端服务传输层只读取原始 STATUS，由公共函数解析为运行/停止/未知；未知不充当退出证据。
显式停止时对可达的所属服务提交幂等 STOP，即使子进程已退出也由服务清理所属路由；
必须收到成功确认，失败保留本次清理责任，不能根据未知 STATUS 发布已停止。
Linux 服务重启必须在旧子进程确认退出并释放 PID 后才替换，停止失败保留旧身份，不启动
第二个实例。启动等待超时统一调用 `stopCore`，覆盖服务、驻留和接管后端；停止失败保留
所有权、PID 文件及可重试状态，并同时报告启动错误和清理错误，不能静默丢失资源引用。

`service_protocol` 覆盖停止失败阻断替换、错误回传、未释放 PID、失败后重试、spawn 失败，
Linux 另使用自有真实子进程验证保留/回收和替换顺序；`runtime_health` 验证应用进程和
CLI detached 入口无法绕过服务启动。实机 TUN/DNS 与跨客户端切换另列验收，不能由这些
隔离用例推断业务目标正常。

## 采用与保留

- 保留远端统计帧新鲜度、有效零流量心跳、退避和每通道三次/五分钟预算、
  暂停/唤醒宽限、Android CommandClient 代次、显式目标诊断及取消。
- 复用旧草稿的有界 gRPC-Web/Protobuf 解码、固定内核原生 API 配置与运行回归。
  没有恢复旧草稿的跨动态 WFP 会话放行方式，也没有恢复停止主 TUN 后拨号的流程。
- 新的原生监听仅在桌面回环 `127.0.0.1:29098`，必须鉴权，关闭 dashboard 下载。
  保留用户其它 services；占用的托管服务 tag 拒绝候选。Android/iOS 不启用该监听。

## 发现并补齐的缺口

| 缺口 | 实际行为 |
|---|---|
| PPTP 查询失败被当成断线 | 服务 IPC 与 Windows RAS 都返回三态证据；只有确认断开才触发自动清理/路由更新，未知保留连接 |
| 控制端口响应遮住所属进程退出 | SCM/root 服务的明确 STOPPED 为进程证据；控制接口另记健康，不替代所属进程状态 |
| 退出检查与切换交叉发布 | I/O 后重新取得生命周期锁并校验运行代次，再发布退出；本地进程句柄读取也受生命周期锁保护 |
| UI 消费者异常锁住通知 | 生产 consumeStreamUpdate 在所有路径确认通知并返回失败，UI 每个消费者只记录一次固定错误；下一有效帧仍可处理 |
| 复制观察者失败锁住通知 | 投递前复制回调抛异常同样释放通知；生产故障注入验证下一次投递恢复 |
| 并发注册返回错误观察者 ID | 在注册锁内保留本次 ID，返回该 ID，支持准确移除 |
| 重置通道复用旧 generation | 通道代次保持递增，旧帧不能在 Reset 后被接受 |
| 有意切换后旧探测污染诊断记录 | 控制结果和恢复记录同时校验运行 epoch、观测代次及暂停状态 |
| 兼容接口与内核原生状态混为一谈 | 独立记录两种结果和采样年龄；启动通过原生 GetVersion/GetStartedAt，诊断核对实例身份 |
| 原生探测可累计多个超时 | 两个 RPC 共用一秒总预算，限制 64 KiB、帧结构和状态码，支持取消；拒绝非回环目标 |
| 增加检查后目标诊断超出预算 | 目标请求使用诊断剩余预算，避免在控制检查之后再追加完整九秒请求 |
| Android 新运行代次沿用统计能力 | start 清除旧 trafficAvailable，首个新 status 才能确认新能力；保留零流量与不可用能力的区别 |
| 桌面以 TUN 配置启动后运行快照仍为默认 false | 启动就绪按已接受运行计划发布 TUN，停止清运行态；不从未实现 TUN 状态的兼容接口覆盖。后续 PPTP 重编译保留实际启动模式 |

原生控制响应、统计有效帧和指定业务目标的 HTTP 响应分别代表不同证据。
不会据零流量自动换节点、重启内核或关闭业务连接。PPTP 的正式配置交接仍需一次重启，
并不保证任意配置增量应用或旧 TCP 会话跨重启保留。

## 回归范围

`runtime_health` 通过生产 WebSocket、原生客户端和真实 sing-box 转发验证：
畸形帧、消费者异常、单通道恢复、鉴权/权限/不支持、兼容接口故障但原生接口
响应正常、暂停/探测交叉、停止/探测交叉及同值 ABA；独立业务请求在故障注入期间持续转发。

`native_control_runtime` 检查原生鉴权、权限、能力、schema、大小及共享期限，
并用固定内核验证本地 rule_set 原子替换、已建立连接保留、坏规则保留上次有效值。
这只是内核已有文件更新能力的验证，不代表应用已提供通用热改出站功能。

Windows 会话状态回归包含 RAS 已连接、断线、无效句柄、权限/过渡状态和接口未知。
物理 DNS 回归检查实际 TCP 对端 PID，隔离 WFP 只影响 `127.0.0.241:53`，
验证普通请求仍被阻止而所属固定内核能查询。服务/WFP 测试需要管理员运行。
这些新回归进入桌面 CMake 必跑门禁。
Windows 回归显式覆盖 APPDATA/LOCALAPPDATA，测试日志写入独占临时目录。

Android 仅运行纯 Java 健康判定回归，不能代表 APK 构建或 Wi-Fi/移动网络/Doze
实机恢复通过。Linux/macOS 和 iOS 本轮未实机验证，iOS 继续暂缓。
诊断中的 TUN 实际网卡、操作系统选路和 DNS 拦截尚未独立检查；指定目标经实际
mixed 入站的响应也不能冒充 TUN 全链路成功。
