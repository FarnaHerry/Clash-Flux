# 明日讨论记录

记录日期：2026-10-01。用户已授权今晚自主开发，以下事项没有阻塞本轮代码，
不需要夜间回答。现有授权继续有效，不把普通实现选择重新变成审批。

## 已采用的实现选择

1. Glaze 使用正式版 9.0.0，隔离为普通 C++ codec，先迁移运行时和内部 policy。
   原生 sing-box JSON DOM、yaml-cpp 和局部规则文本编辑保留，未直接整文强类型化。
2. 继续固定 sing-box 1.14.2；移动端只共享编译器能力，不增加普通代理多订阅编排。
   桌面唯一主订阅 + 多次订阅仍是既定最终设计，不提前用界面冒充已实现。
3. 不可转换的逻辑子条件和 inline provider payload 整体拒绝并进入账本；不保留
   半条条件扩大匹配，不用内置 CN 内容代替转换失败的同名显式 provider。
4. DNS/代理循环返回编译错误；不去掉代理绑定后直连。直连专用解析时机、MPTCP
   IPv6 与 detour 忽略物理字段明确记 approx。
5. 保留旧库、原生未知 JSON 字段、证书校验、Android 后台所有权及国内 GEO 打包步骤。

## 可以明日讨论的产品偏好

| 事项 | 当前选择 | 可讨论问题 |
|---|---|---|
| 高级原生配置入口 | 保留导入原生 JSON；本轮先完成编译与诊断边界 | 第一批可视化字段编辑优先 DNS、拨号选项，还是 WireGuard 端点？ |
| 规则集来源界面 | 已接 inline 子集；外部 provider 尚无完整下载/转换生命周期 | 独立规则集页面还是订阅详情内管理？是否有日常使用的 YAML/text/MRS 样本供下一阶段覆盖？ |
| Glaze 后续生成器迁移 | 配置 IR 先建字段 presence、未知片段与来源，再替换 DOM builder | 是否优先全配置编辑器的可维护模型，还是继续按实际常用协议补字段？两者均在既定方向内 |
| 桌面编排交互 | 按已写入文档的主/次角色、稳定对象与默认阻断设计 | 可以在模型与失败回滚实现后评审具体页面；今晚未创建空壳多订阅 UI |
