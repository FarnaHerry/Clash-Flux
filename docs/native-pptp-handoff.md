# Windows PPTP 与主 TUN 的连接交接

2026-10-24，基于 `1a1659b` 加本地未提交修改，固定官方 sing-box 1.14.3。

连接 PPTP 时保留当前主内核和 TUN。Windows 服务先解析真实服务器地址、
安装会话所有的物理出口 /32，并用 `GetBestRoute2` 确认出口确实为物理网卡；
已有 TUN /32 等路由仍抢占时拒绝拨号，不提前停止主内核。

严格 TUN 会阻止服务进程直接发送普通 DNS。服务使用同目录固定官方内核，
短暂启动只有回环 SOCKS 入口和绑定物理网卡的 direct 出站的独立配置，
经随机 SOCKS 认证向物理网卡 DNS 的 IPv4 地址发送 TCP DNS 查询。
该进程复用 sing-tun 对所属内核可执行文件身份已有的许可；不创建 WFP 放行规则，
不修改系统 DNS，不添加影响其它程序的 DNS /32，不加载用户订阅或启动另一张 TUN。
进程由私有 Job Object 持有并限时回收，配置、诊断文件和句柄随查询清理。
解析要求物理 DNS 支持 TCP；失败保留主内核并给出错误。

不使用跨动态 WFP 会话的放行：Windows 不支持引用另一动态会话的动态子层。
官方 `tools connect` 在当前 Windows 构建的管道输入实测失败，也没有用于生产。

RAS 禁用默认网关和自动类路由。PPTP 建立后，服务先在仍活动的主 TUN 上准备
PPP 路由捕获，再安装明确的内网路由，避免 PPP 的更具体路由绕开主规则。
旧服务没有 `PPTP_LIVE_DIAL` 能力时拒绝在活动 TUN 下连接，提示更新服务。
Windows 同时只允许一条 PPTP 的边界不变。

配置交接先在旧内核运行时完成 provider/GEO 准备、编译、selector 投影、
固定内核 check 和独占文件暂存。停止旧内核后直接原子提交这份已检查配置，
不再重新下载、编译或检查。仅路由刷新生成完全相同 JSON 时跳过重启；
显式重启仍执行。配置失败保留旧运行计划，恢复失败只在旧原生接口仍有效时回滚。
拨号前的实际 TUN/系统代理状态用于恢复，不在失败后读取被停止动作改写的状态。
桌面启动就绪时从已接受计划写回 TUN 运行模式，停止时清运行态；兼容
`/configs` 不作为 TUN 状态来源。此前以持久化 TUN 意图启动却未发布运行模式，
后续原生路由重编译可能误生成无 TUN 配置。

与远端运行健康功能合并后，保留 lifecycle 锁、`pauseHealth()` 和 runtime epoch：
有意的停止/重启不触发健康误判，过期状态不能覆盖新运行代次。
日志分别记录拨号、候选准备和控制器就绪耗时；这些不是端到端网络中断时长。

2026-10-25：吸收早期草稿的原生 gRPC-Web 代码。启动以 `GetVersion` 和
`GetStartedAt` 确认版本及实例，健康诊断分别记录原生控制、兼容接口和统计通道。
PPTP 会话采用“连接/断开/未知”证据；IPC 失败、RAS 状态暂不可读或接口信息
暂不可读不能触发断开和主计划重写。临时 DNS 出口在发送随机认证及查询前，
核对已连接 TCP 对端确实属于服务创建的子进程。联合复核见
[运行健康实施复核](runtime-health-review.md)。

新增出站或改变接口的完整配置仍需一次主内核交接，不能宣称任意配置增量生效，
也不保证已有 TCP 会话跨重启保留。官方本地 rule_set 文件更新能力不等于动态增删出站。

验证入口：

```powershell
cmake --build build --target clash-flux test_windows_physical_dns test_windows_service
ctest --test-dir build -R '^(windows_physical_dns|runtime_health|compensation|vpn)$' --output-on-failure --no-tests=error
# 下列隔离 WFP 测试需要管理员；只过滤 127.0.0.241:53，不访问真实 DNS。
./build/pptp-native/test_windows_physical_dns.exe --require-wfp
```

WFP 用例断言普通查询被阻止、所属内核原生出口能查询、结束后原阻止规则仍有效。
普通用例检查分片 TCP 报文、请求 ID 错误及 DNS 错误码拒绝。
2026-10-25 使用已授权“双辽”实机拨号。首次拨号 6908 ms、旧内核运行期间
候选准备 1840 ms、控制器就绪交接 3019 ms；原生接口采样就绪间隔约 2.79 秒，
不是精确的业务断网时长。三分钟观察 340 次原生采样均成功、实例不变，
12 次通过实际 mixed 入站请求既有 urltest 目标均返回 HTTP 204。
诊断回读原生/兼容接口响应、实例匹配，PPTP connected=1/unconfirmed=0，
两路统计 fresh；操作系统回读 PPTP 服务器仍走物理 WLAN。

断开测试发现订阅卡引用未打包文案“断开中…”导致 GUI 异常退出；
补齐“断开中…”的中英文/默认资源，并对连接→断开→重新连接显示在中英文及默认
语言下挂载真实资源包回归。其余成功/失败反馈遗漏也已补齐，源文案全量检查进入门禁。
修复后从保存的 TUN 意图启动，连接及断开“双辽”均保留所属主 TUN；断开后
PPP 接口已移除、GUI 存活。额外 30 秒采样 56 次均响应且实例不变，
3/3 mixed 入站目标请求返回 HTTP 204。最终恢复内核/TUN/系统代理关闭及原托盘设置。
该订阅使用 IP 地址且未配置内网路由，未提供内网目标；不声称实机域名解析
或内网业务验证通过，物理 DNS 仍由上述隔离用例验证。
