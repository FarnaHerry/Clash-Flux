以 50,000 条 Clash 规则为例，原文读取约 1 ms，转换、捕获与冷索引耗时 287.85 ms，投影耗时 14.10 ms。JSON 与 CBOR 的产物读取分别为 3.54 / 2.47 ms，校验 4.87 / 4.15 ms，解码 42.69 / 72.60 ms，恢复模型 41.41 / 33.24 ms，投影 10.14 / 10.75 ms。分段取各自中位数。JSON 就绪范围为 97.81–106.25 ms，重建为 294.72–331.80 ms。

同一组 JSON 与 CBOR 的编码及校验中位数为 87.20 / 71.27 ms，缓冲写入为 2.18 / 1.70 ms。重建与 JSON 恢复的目标模型分别记账 44.07 和 42.58 MiB，均已超过页面缓存的 32 MiB 闲置预算；页面投影和应用其它缓存另计。落盘可以减少大样本准备峰值，恢复后的活跃模型仍需近似的常驻空间。完整分段、7 次样本、记账和 RSS 见 [原始 CSV](2026-11-16-target-r5.csv)。

## 结论与试点设计

应用当前每次重启从原文准备目标模型。大型自包含 Clash YAML 值得用真实首次打开数据验证 JSON 试点，10,000 和 50,000 条样本分别节约约 36 和 199 ms。JSON 在测试中就绪更早、峰值 RSS 更低或接近 CBOR，代价是产物体积约为原文的 3.3 倍。CBOR 体积约比 JSON 小 25%，适合在目标设备的读取成本主导时再复测。小样本只节约几毫秒，50,000 条原生 JSON 也只节约约 29 ms，却要多写近 10 MiB。试点范围优先选大型自包含 Clash 来源。

1. 首轮候选为版本化 JSON 信封及顺序化规则、默认动作、目录、诊断、出处和 rule_set。选取可确认转换依赖的 Clash 来源。源 ID、完整原文字节及格式、转换语义与 schema、目标平台和实际内核能力、本次转换默认值及资源内容均参与身份校验。内联 provider 随原文签入同一身份，文件、远端和平台资产在没有可靠内容快照时走原文重建。摘要可查找派生文件，加载时再核对完整身份与正文完整性。
2. 只在权威原文版本通过提交、当前任务仍匹配且捕获成功后，由应用任务单飞生成；写入应用私有缓存根，在同一目录独占暂存后原子替换。重启按当前权威来源请求加载，校验来源、大小、深度、数量和结构后再构造拥有型模型。仅保留可安全持久化的来源，转换结果含敏感信息的来源继续从原文准备。
3. 按来源修订管理派生文件，替换或删除只作用于该来源的缓存。按设备实测的额外磁盘、RSS 和写入预算淘汰。旧任务晚到时放弃发布；版本未知、损坏、失配或驱逐时从权威数据重建。原文不可用时返回明确错误。既有修改重放、资源检查、运行上下文和固定内核候选检查继续执行。

上述生命周期供后续试点。试点前先测代表性真实订阅的重启和首次打开，分离当前后台预生成是否已隐藏等待、原文及产物的设备读取耗时、UI 挂载与全应用峰值 RSS，并验证写入和淘汰预算。

在 Linux Release 应用的后续首次打开测量中，1 万条合成规则受益于预生成；5 万条快照超出闲置预算时先被预生成、再被页面重建。该结果将试点重点收窄到留不住的目标快照与按需加载。见 [首次打开测量](2026-11-16-target-r5-first-open.md)。

## 方法与验证

Clash 合成样本含域名规则、内联 provider、未支持条目、MATCH 与尾随条目；原生样本含路由规则、不透明字段、uint64 上限、int64 下限和浮点数。`rebuild` 经过现有冷目标索引、`compileConfig` 与 `ProjectTargetSource`。产物恢复调用相同的 `TargetCapture` 构造真实模型，保留目标规则的私有 JSON 和来源管理数据，不在盘上复制原文或存运行配置。独立验证进程核对完整产物、个人规则投影、候选编译 JSON、诊断、警告、复用计数与追溯；也验证了截断、未知版本和源字节变化被探针拒绝。探针身份固定于合成样本，生产失效、权限、原子发布和回退仍属于试点实现范围。

在已就绪的 Linux 开发环境中从仓库根运行以下命令。
