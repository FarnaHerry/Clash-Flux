# 桌面内核、代理监听与流量接管

桌面将内核生命周期与代理连接分开，Android 的后台/VPN 生命周期不随此次调整改变。

| 典型状态 | 内核控制面/出站 | 业务入站 | 系统代理 | TUN |
|---|---|---|---|---|
| 待命 | 就绪，可测速和选节点 | 暂停 | 未接管 | 关闭 |
| 仅监听 | 就绪 | 开放 HTTP/SOCKS 等配置端口 | 关闭 | 关闭 |
| 系统代理 | 就绪 | 开放 | 指向本应用 | 关闭 |
| TUN 接管 | 就绪 | 开放 | 可选 | 按运行计划启用 |

后两种不是互斥模式，系统代理和 TUN 允许同时生效。系统代理仅影响遵循该设置的应用，
TUN 按路由配置接管；都不代表已验证节点的公网可用性。仅监听时，应用可以手动设置
HTTP/SOCKS 代理，因此两个接管开关都关闭仍是有效连接。首页不以实时字节数判断连接，
空闲不关闭会话、不重置计时。

## 运行原语与发布

- `CoreAction::Start` / `startReadyCore` 让内核待命；`Connect` / `connectProxy` 开放代理
  监听并应用保存的系统代理/TUN 选择；`Disconnect` 撤销自有接管、断开原生连接后重新待命。
  `Stop` 仍是完整停核，保留于托盘和应用退出，不将断开连接等同于停核。
- 应用启动完成持久化和服务版本检查后默认待命，不主动安装服务或请求 UAC。已有
  `app.auto_run` 键保留，界面改称“启动时自动连接”；缺省 false，true 直接恢复代理连接。
- `CompileOptions::proxyListening` 默认 true，普通编译与显式 CLI `core start` 保留原行为。
  桌面待命显式传 false，暂停全部配置业务 `inbounds`，保留控制接口、出站、节点选择、
  DNS 和路由。原生配置和订阅原文不改写；连接时重新完整编译并恢复原有入站。
  无业务入站的待命允许与其他客户端的全局 TUN 共存；显式连接仍检查接管冲突，
  候选 TUN 的接口名和地址冲突检查始终保留。待命测速可能经过已有隧道，不保证物理直连。
  `proxyListening=false` 与 `tunInbound=true` 的矛盾计划被拒绝。
- 开放监听沿用完整候选准备、检查、原子提交和交接，准备失败保留原内核与运行计划。
  完整配置切换仍可能重启 sing-box，不承诺内核原生不具备的入站热切换。
- `CoreSnapshot::proxyListening` 来自成功接受的计划；`CoreView::ProxyActive()` 同时要求
  内核 Running。`connectedSince` 从开放监听成功开始，正常重配/回滚保留，断开清除；
  `runningSince` 继续表示内核控制面就绪时间。首页和托盘共用应用级 CoreControl。
- 系统代理/TUN 开关保留独立意图，待命时只保存，下次连接应用；连接中立即重配。
  停核/断开不清除选择，也不撤销其它客户端的系统代理。系统代理实际指向、运行 TUN、
  代理监听和服务安装状态分别显示/探测，不把勾选意图当实际接管。

通过内核下载订阅需要已开放本地代理端口；待命测速通过控制接口直接测试出站，
不会为测速打开代理端口或恢复系统代理/TUN。现有节点 URL、TLS 校验与保真度记账不变。

## 验证入口

`singbox` 覆盖完整编译与状态清除；`proxy_standby_runtime` 用固定官方内核及回环 HTTP
目标验证 Clash YAML/原生 JSON 的待命→仅监听→待命：控制面及 URLTest 均可用，
待命端口拒绝连接，仅监听时真实 HTTP 请求通过代理。测试不修改系统代理或创建 TUN。
生产标题/动画使用 `page_transition`，文案使用 `ui_resources`；系统接管仍需平台实机验收。

服务手动安装/更新成功后，设置入口默认拉起待命内核；若安装由连接、TUN 等显式操作触发，
则保留应用级操作票据，安装后继续原始命令及参数，不强制覆盖成待命。服务替换后先撤销旧客户端
运行态，再启动或恢复原命令；安装取消/失败不执行原命令。启动时服务同步仍沿用启动设置。
